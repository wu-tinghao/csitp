# 建议实施与实验计划

[返回首页](../README.md)

本页是基于调研提出的**本项目设计**，不是现有论文已完成的功能，也不是已经实现的代码。

## 1. 最小可行系统

第一版固定一个 PCB 或钢材数据集，边缘使用 YOLOv8n。云服务器首先承担训练、验证和模型分发；第二步加入较大检测模型的按需复检。无需把 VLM 作为云端必选模型。

~~~mermaid
flowchart LR
  Camera[产线相机或离线回放] --> Edge[边缘轻量检测]
  Edge --> Route{路由策略}
  Route -->|本地可判| Result[结果记录与分拣接口]
  Route -->|疑难且满足时限| Cloud[云端较大模型]
  Cloud --> Result
  Route -->|超时或断网| Review[隔离或人工复核]
  Edge --> Queue[样本与结果持久队列]
  Queue --> Label[标签确认与数据管理]
  Label --> Train[云端训练与验证]
  Train --> Registry[模型版本与发布门控]
  Registry --> Edge
~~~

普通电脑也可先承担云端角色；边缘进程限制 CPU/内存的模拟只能验证逻辑，不能冒充真实板卡结果。工业相机未到位时使用带时间戳的数据回放，并在报告中注明。

## 2. 三步交付

| 阶段 | 做什么 | 完成证据 |
|---|---|---|
| 1 边缘基线 | 训练 YOLOv8n，导出并部署；固定测试划分 | 可重跑脚本、模型版本、板卡运行日志、每类召回及延迟 |
| 2 R1 编排 | 数据回流、云训练任务、验证门控、模型下发、失败回滚 | 两个模型版本切换演示；记录发布成功率和停顿时间 |
| 3 R2 策略 | 边缘疑难筛选、云端检测、超时降级、结果合并 | 边缘独立/全部上云/固定阈值/自适应路由四组实验 |

Sedna/DDA 可用来理解接口和做框架对比；第一版也可用 Python 服务与消息队列独立实现核心流程，再决定是否迁入完整框架。不能同时承诺联邦学习、VLM、分支网络和自动重训全部完成。

## 3. 实验指标

- 检测：mAP50、mAP50-95、每类召回、漏检率、误报率。保持同一测试集和标注规则。
- 边缘成本：模型大小、峰值内存、功耗（有仪表才报告实测）、预处理/推理/后处理分别耗时。
- 系统时延：采集或回放输入到最终可执行判定的 p50/p95/p99；单独记录上传、排队、云推理和回传。模型 FPS 不代替产线吞吐。
- 协同成本：上云图像比例、每图上传字节、云调用次数和超时率。准确率不能只在“成功返回的样本”上统计。
- 可靠性：网络断开、云服务失败、版本加载失败时，是否丢样本、重复执行或误放行。
- 发布：校验成功率、切换停顿、回滚耗时及版本追溯。
- R3 可选：相同标签预算下，从头训练/仅微调/域适应的精度与适配时间。

## 4. 对照和防止结果失真

1. 所有方法使用同一测试集；按 PCB 原板/工件/采集批次分组，避免同图增强或同一工件同时进训练与测试。
2. 调阈值用验证集；固定测试集后不再用它调整路由和模型。
3. 全部上云基线必须包含实际上传和排队，不只量 GPU 前向时间。
4. 云端不是标准答案：用人工确认标签评价云、边和冲突决策。
5. 对“无检测框”的样本也抽查并统计漏检，避免路由只覆盖已经发现的缺陷。
6. 比较断网前后队列积压、重传、去重；补传成功不代表曾错过的实时分拣可以补救。
7. INT8 与高分辨率分别做消融，检查微小缺陷召回是否恶化。
8. 保留随机种子、数据版本、模型哈希、设备配置、输入尺寸和原始逐图测量。

## 5. 可向导师解释的研究重点

研究“在边缘算力、网络带宽和产线节拍限制下，如何安排推理、复检和模型更新，使漏检、时延和云端成本达到更合适的平衡”。先以实验证明改进，不把“用了 YOLO + 云服务器”直接等同创新。
